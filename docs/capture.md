# Relay

Click the Relay bar at the top of the map (or under Search in the sidebar), or press Command/Ctrl+Shift+K. Settings → Relay changes or turns off that shortcut; it is stored in this browser. Relay is the one verb for handing work off: a typed thought here, or **Relay** on a note (see the README). Thoughts route asynchronously. A thought that matches a project goes to that project's chief as a `<relay>` message. The chief decides what it needs (an answer, a logged fact, a note, canvas cards, images or charts, tasks, a workspace or session for you, a routine, a scout, one worker or several) and settles it with `relay_report`, which returns an answer to the Inbox. The thought's **Open session** link is the chief's session. Project tags pin routing. Unmatched thoughts have no chief: they run as a read-only scout in Home, as before.

The router tries twice with a 45-second deadline per attempt. Routing failures offer Retry; interrupted sessions offer Resume unfinished work. Thoughts under way are listed at the top of the Inbox. An answer with a blocking decision appears in Decisions; other answers stay in Updates & answers. Related events are grouped by request. Every distinct consequential action retains its own approval. Ready thoughts can continue, receive a redirect, be closed, or discarded. A redirect with another project's tag archives the previous isolated workspace and routes a fresh worker. The original thought remains in the capture text. You can save the redirect as a Home routing rule.

Discard cancels work and archives isolated workspaces; it never archives the shared scout workspace. Undo restores the record and workspace, but does not automatically restart cancelled work. Archived worktrees retain their files under the existing housekeeping policy.

The limit defaults to eight open captures. Set `maxOpen` in `~/.thunk/config/capture.json` (or under `THUNK_DATA_DIR`). Closed and discarded records no longer count. Relay-ready notifications appear in Needs you delivery settings and are the ready thought's row in the Inbox; they close through Close conversation or Discard; replying or approving a specific next step starts another pass. Reading an answer does not close it.

The desktop app also registers an OS-wide shortcut (default Alt+Space) that opens a small Relay window over whatever app is in front, while Thunk is running. On macOS the window is a non-activating panel: it floats over full-screen apps on any Space, takes typing without bringing the main Thunk window forward, and leaves you in the app you were using when it closes. Pressing the shortcut again closes it. If another app holds the shortcut when Thunk starts, it is off and Settings → Relay says so. Change it there, and turn on Open Thunk at login (macOS and Windows) to keep it working after a restart. It is stored on this computer, including when connected to a remote backend. Submission, Escape and blur hide the capture window. Mobile has a Relay navigation button. Browser drafts survive dismissing the bar within the tab.

First-pass restrictions are worker instructions: no pushing, PRs, merging, deploying or sending before approval. Existing worker tool permission handling still applies. Go ahead authorizes the displayed next step only.

Relay workers receive the original text, the router's provisional brief, and its unverified assumptions. They are instructed to infer the intended outcome, read relevant existing notes, memory and tasks, resolve uncertainty from evidence and preferences, and produce a useful first draft or result. Low-cost reversible assumptions should allow progress; questions are reserved for consequential choices that cannot be resolved from available context. Saved facts need not generate additional work. Scouts can deliver drafts in their response without writing files.

A completed first pass can report `needs_person: none`. It remains available for review, Close conversation, Discard or Reply, but has no Go ahead button. Go ahead is available only for a specific held-back step; the server rejects continuation without one. This guidance uses the worker's existing context and tools; it does not add a separate retrieval or review agent, or guarantee that the model follows every instruction.

A chief-handled thought comes back as a conversation headed **Chief · Answered**: what you asked, what the chief reported, and a reply field. After sending, **Queued** means the message is saved behind the chief's current turn; **Working** means it has been delivered; **Answered** means the chief reported back. The saved conversation stays accessible while you wait, including your latest reply. Reports from an older turn cannot answer a newer queued reply.

**Close conversation** files the conversation and removes it from the open-thought limit. It does not approve a held-back step, complete tasks, cancel workers, or merge changes. **Go ahead** approves only the displayed step. **Discard** cancels the request: for a chief it sends an explicit stop instruction for that request's workers. **Open the chief** opens its session.

Interrupted requests show the stopping reason (including provider errors or a server restart), completed-task counts when available, and **Resume unfinished work**. The same request and saved conversation go back to the chief with its existing task ledger. Routing is not repeated. Repeated delegation of a linked task reuses that task, including completed tasks; unfinished workers continue through their existing sessions. Older requests without links ask the chief to inspect history and existing tasks first. Recovery does not grant fresh approval for consequential actions.

Receipt and session state are reconciled every ten seconds and at startup. A stopped session is detected on the next check. An idle chief gets a short 30-second allowance to persist its report; if it never reports, the Inbox explains that specific condition instead of waiting five minutes. Only workers and queued tasks linked to this request keep it working; unrelated project work cannot conceal an interruption. A late report can still settle an interrupted request.

A ready thought whose worker changed code shows the same three parts as a Changes to review card: Changes (diff stat, Review diff and Request changes), Trial merge (latest result, out of date when the branch moved, Run again) and Pull request (Open PR, checks, link). Open PR is always a click; nothing pushes or opens a PR on its own. When the task has acceptance criteria, a Criteria table lists what Thunk checked and what the worker says for each (see Criteria and evidence in the README).

Delivery has a separate meaning from an answer: **Work completed** is the worker's task outcome; **Ready for review** is an open, non-draft pull request; **Merged** requires GitHub's merged state. Drafts and PRs closed without merging are labeled separately. Passing checks, answering a conversation, and closing it do not imply a merge. Routine progress stays folded under its request and does not raise desktop alerts; blockers and approvals remain visible.
